# Дизайн: запись ученика из принятой заявки в календарь репетитора

## Контекст

Сейчас календарь репетитора уже умеет:

- создавать урок вручную по дате и времени;
- записывать в свободный слот ученика, который не связан с платформой.

Backend уже поддерживает создание урока по `applicationId` в `crm-service`: если передан `applicationId`, урок связывается с принятой заявкой и карточкой ученика; если `applicationId` нет, создается ручной урок для внешнего ученика.

Проблема сейчас только во frontend/API-потоке календаря: в интерфейсе календаря нельзя выбрать ученика из уже принятых заявок платформы прямо в ячейке календаря.

## Цель

Дать репетитору возможность в календаре:

- добавить занятие в ячейку для ученика из уже принятой заявки платформы;
- сохранить текущую возможность вручную записать ученика, которого нет на платформе.

## Не меняем

- Не меняем текущую backend-логику создания урока по `applicationId`.
- Не убираем ручной сценарий записи внешнего ученика.
- Не показываем в календаре новые или отклоненные заявки.
- Не добавляем оплату, автоназначение или сложную синхронизацию между страницами.

## Рекомендуемый подход

В обеих календарных модалках (`Новое занятие` и `Записать ученика`) добавить переключатель источника:

- `Из принятых заявок`
- `Вручную`

Поведение:

- если выбран режим `Из принятых заявок`, форма показывает список только принятых заявок текущего репетитора, доступных для назначения;
- если выбран режим `Вручную`, форма работает как сейчас и отправляет `studentName`, `subject`, `format`.

## Правило отбора заявок

В список для календаря попадают только заявки:

- со статусом `ACCEPTED`;
- принадлежащие текущему репетитору;
- по которым еще не создан урок.

Последний пункт нужен, чтобы один и тот же принятый лид не назначался повторно как первый урок из календаря.

## UI-решение

### 1. Модалка "Новое занятие"

Форма получает новый блок:

- переключатель `Из принятых заявок` / `Вручную`;

При режиме `Из принятых заявок`:

- поле выбора заявки (`select` или список карточек);
- в подписи к варианту показываются:
  - имя ученика;
  - предмет;
  - формат;
  - желаемое время из заявки;
- после выбора заявки поля ученика вручную не показываются;
- при сохранении отправляется:
  - `applicationId`;
  - `startsAt`;
  - `durationMinutes`.

При режиме `Вручную`:

- остается текущая форма даты, времени и длительности;
- добавляются поля:
  - `Имя ученика`;
  - `Предмет`;
  - `Формат`;
- при сохранении отправляется текущий ручной payload без `applicationId`.

### 2. Модалка "Записать ученика" для свободного слота

Форма получает тот же переключатель:

- `Из принятых заявок`
- `Вручную`

При режиме `Из принятых заявок`:

- выбирается заявка;
- дата и время слота остаются фиксированными;
- при сохранении отправляется:
  - `applicationId`;
  - `startsAt`, собранный из даты и времени слота;
  - `durationMinutes`, рассчитанный из слота.

При режиме `Вручную`:

- остается текущая форма `Имя ученика` + `Предмет` + `Формат`;
- поведение остается прежним.

## API-решение

### Новый endpoint

Добавить в `crm-service` endpoint:

- `GET /api/tutor/lesson-candidates`

Ответ:

```json
[
  {
    "applicationId": "uuid",
    "studentId": "uuid",
    "studentName": "Иван Иванов",
    "subject": "Математика",
    "format": "Онлайн",
    "desiredStartTime": "2026-05-08T17:00:00",
    "gradeGoal": "8 класс · подготовка к ОГЭ"
  }
]
```

`studentId` полезен как контекст для дальнейшего развития CRM, но для создания урока в текущем контракте главным остается `applicationId`.

### Источник данных

Кандидаты собираются из:

- `CrmApplication` со статусом `ACCEPTED`;
- связанной `StudentCard`, созданной после принятия заявки;
- `Lesson`, чтобы исключить заявки, уже использованные для назначения урока.

### Создание урока

Контракт `POST /api/tutor/lessons` не требует ломающих изменений.

Используются два сценария:

1. Через заявку:

```json
{
  "applicationId": "uuid",
  "startsAt": "2026-05-08T17:00:00",
  "durationMinutes": 60
}
```

2. Вручную:

```json
{
  "startsAt": "2026-05-08T17:00:00",
  "durationMinutes": 60,
  "studentName": "Иван Иванов",
  "subject": "Математика",
  "format": "Онлайн"
}
```

## Изменения по слоям

### Backend

- добавить DTO кандидата для урока;
- добавить сервис/метод выборки кандидатов из принятых заявок;
- добавить endpoint `GET /api/tutor/lesson-candidates`;
- исключать кандидатов, по которым уже есть урок;
- добавить узкий тест на фильтрацию кандидатов.

### Frontend API

- добавить `getTutorLessonCandidates()` в `frontend/src/shared/api/tutor.ts`;
- добавить тип `TutorLessonCandidate` в `frontend/src/shared/types.ts`.

### Frontend UI

- обновить `TutorCalendarPage.tsx`;
- использовать единый набор состояний для режима записи ученика;
- показывать список кандидатов в обеих модалках;
- сохранить существующий ручной сценарий без регрессии.

## Ошибки и граничные случаи

- Если принятых заявок нет, в режиме `Из принятых заявок` показывается понятный empty state и кнопка переключения на `Вручную`.
- Если заявка была назначена в другой вкладке раньше сохранения, backend возвращает ошибку конфликта; frontend показывает понятное сообщение и предлагает обновить календарь.
- Если слот или время уже заняты, остается текущая backend-проверка пересечений.

## Тестирование

Минимальная проверка после реализации:

- backend: узкий `mvn test` в `backend/crm-service`;
- frontend: `npm run typecheck` из `frontend/`.

Дополнительно вручную:

- в календаре можно создать урок из принятой заявки;
- в календаре по-прежнему можно вручную записать внешнего ученика;
- одна и та же принятая заявка не отображается повторно после назначения урока.

## Риски

- В текущем UI календаря две разные модалки создают урок похожим, но не полностью общим способом; при реализации важно не разъехать по поведению между ними.
- Если в продукте позже понадобится несколько уроков по одной заявке, фильтрацию "без созданного урока" придется уточнить до "без первого урока" или перенести логику на другой признак.

## Решение для реализации

Реализуем вариант 1:

- в календаре оставляем ручной сценарий;
- добавляем запись из принятых заявок;
- используем новый endpoint с узкой выборкой кандидатов;
- создаем урок по существующему `applicationId`-контракту без ломающих изменений.
